Учитывая твой стек (Laravel, Vue 3, TypeScript) и интерес к AI‑инструментам (SourceCraft, Qwen и т. п.), есть несколько рабочих способов хранить историю промптов и их результатов прямо в проекте — от простых до полноценных систем.

---

## Простой вариант: файлы в репозитории (лучше всего для начала)

Создай папку `prompts/` в корне проекта и структурируй по назначению:

```
prompts/
  backend/              # Laravel, API, логика
    generate-controller.md
    refactor-service.md
  frontend/             # Vue, компоненты, логика
    generate-component.md
    optimize-composition-api.md
  ci-cd/                # автогенерация конфигов, скриптов
    github-actions-deploy.md
  history/              # сюда складывай результаты/примеры
    2026-09-10_generate-controller_v1.json
    2026-09-11_generate-controller_v2.json
```

**Что хранить в файлах:**

- **Промпт** — в `.md` или `.txt`.
- **Параметры вызова** (модель, температура, max_tokens) — в отдельном `.json` рядом.
- **Результат от модели** — в `history/` как JSON с метаданными: дата, модель, версия промпта, ID задачи (Jira/GitHub issue), статус («принято», «доработать», «отклонено»).

**Пример `prompts/backend/generate-controller.md`:**

```markdown
# generate-controller

## Назначение
Генерация Laravel-контроллера по спецификации эндпоинта.

## Контекст
Используем Laravel 11, RESTful стиль, DTO в запросах, исключения через `App\Exceptions\ApiException`.

## Промпт
Ты — опытный Laravel-разработчик. Напиши контроллер для эндпоинта POST /api/orders.
Требования:
- Валидация через Form Request
- Логика в Service слое
- Возвращай JSON с полями: id, status, created_at
- Обработай ошибки валидации и бизнес-ошибки через ApiException

## Примеры (входные данные)
Пример спецификации:
{
  "method": "POST",
  "path": "/api/orders",
  "fields": ["customer_id", "items"]
}

## Ожидаемый результат
Контроллер с методами, типизациями, комментариями, без лишнего кода.
```

**Пример JSON‑метаданных:**

```json
{
  "prompt_file": "prompts/backend/generate-controller.md",
  "model": "qwen-plus",
  "temperature": 0.2,
  "max_tokens": 1024,
  "timestamp": "2026-09-10T14:23:00Z",
  "task_id": "TASK-123",
  "status": "accepted",
  "result_file": "history/2026-09-10_generate-controller_v1.json"
}
```

**Плюсы:** всё в Git, прозрачно, легко ревьюить, можно откатить версию промпта.  
**Минусы:** не годится для больших объёмов результатов (JSON‑файлы быстро раздувают репозиторий).

## Полуавтоматический вариант: Skills/Rules‑файлы + логирование в БД

Если ты используешь SourceCraft/Qwen в агентском режиме, удобно вынести правила в файлы вроде `SKILL.md` / `RULES.md`, а результаты писать в базу.

**Файл правил (в корне):**

- `SKILL.md` — для SourceCraft (навыки агента).
- `PROMPT_REGISTRY.md` — реестр промптов: краткое описание, путь к файлу, версия, когда обновлялось.

**Логирование результатов в БД:**

Создай таблицу `ai_prompt_logs`:

```sql
CREATE TABLE ai_prompt_logs (
  id BIGSERIAL PRIMARY KEY,
  prompt_key VARCHAR(255) NOT NULL,        -- например, 'generate-controller'
  prompt_version VARCHAR(50) NOT NULL,    -- 'v1', 'v2'
  model VARCHAR(100) NOT NULL,             -- 'qwen-turbo', 'sourcecraft-pro'
  input_payload JSONB,
  output_payload JSONB,                   -- сам ответ модели
  metadata JSONB,                         -- task_id, user, status и т.д.
  created_at TIMESTAMP NOT NULL DEFAULT NOW()
);
```

В Laravel это будет Eloquent-модель `AiPromptLog` и сервис `PromptLogger`, который вызывается сразу после запроса к LLM.

**Плюсы:** история результатов не раздувает Git, можно искать/фильтровать по task_id, модели, статусу; удобно для аналитики качества промптов.  
**Минусы:** нужно поддерживать схему и миграции, следить за размером `output_payload`.

## Продвинутый вариант: векторный поиск по промптам + RAG‑база знаний

Если промптов становится много и хочется быстро находить «тот самый» промпт по смыслу, а не по названию:

1. **Хранишь тексты промптов** в файлах или в БД.
2. **Генерируешь эмбеддинги** (например, через локальную модель или API) и сохраняешь в векторной БД (pgvector в PostgreSQL, Chroma, Qdrant).
3. **Делаешь поиск по смыслу**: «найди промпт, который генерирует контроллеры с валидацией».

Для твоего стека: PostgreSQL + pgvector — идеально, потому что у тебя уже может быть Laravel + Postgres.

**Плюсы:** быстрый семантический поиск, можно строить RAG поверх своих промптов (например, подсказывать агенту «используй промпт X» на основе схожести запроса).  
**Минусы:** больше инфраструктуры и кода.

## Интеграция с CI и ревью

Чтобы история промптов была полезной, а не «архивом», придерживайся простых правил:

- **Отдельные коммиты** для изменений промптов, в сообщении — кратко «prompt: generate-controller v2 — добавлена валидация DTO».
- **Ревью промптов** как кода: если коллега меняет промпт, это проходит PR.
- **Версионирование**: в имени файла или в метаданных явно указывай версию (`v1`, `v2`) и ссылку на задачу.
- **Не храни секреты** в промптах и результатах (ключи, пароли, чувствительные данные).

---

## Практические советы под твой стек

- **Для Laravel**: используй консольные команды или Jobs для вызова LLM и сразу логируй в `ai_prompt_logs`. Это легко покрыть тестами и деплоить вместе с проектом.
- **Для Vue 3**: если используешь AI для генерации компонентов, храни промпты в `prompts/frontend/` и при генерации сохраняй diff результата (старый код vs новый) в истории — так проще ревьюить изменения.
- **Для SourceCraft/Qwen**: положи `SKILL.md` в корень, чтобы агент всегда видел актуальные правила, а результаты сохраняй либо в Git (для простых задач), либо в БД (для регулярных задач).

---

## Что выбрать прямо сейчас

- **Если нужно быстро и просто**: папка `prompts/` + JSON‑логи в `history/`, всё под Git. Подходит для прототипов и личного проекта.
- **Если делаешь продукт и нужна воспроизводимость**: `prompts/` под Git + таблица `ai_prompt_logs` в БД. Это даст и контроль версий промптов, и историю результатов без раздувания репозитория.
- **Если планируешь RAG/поиск по промптам**: добавь pgvector и семантический поиск.
