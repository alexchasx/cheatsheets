**`EXPLAIN` в PostgreSQL** — это команда, которая показывает **план выполнения запроса**: какие операции сделает база, в каком порядке, какие индексы использует, сколько строк ожидает обработать и сколько это «стоит» по оценке планировщика.

Учитывая, что ты изучаешь SQL (в т.ч. для собеседований) и работаешь с бэкендом (PHP/JS), `EXPLAIN` — один из главных инструментов, чтобы понять, почему запрос тормозит, и обосновать создание индекса или переписывание запроса.

---

## Базовый синтаксис

```sql
EXPLAIN SELECT * FROM users WHERE email = 'test@example.com';
```

По умолчанию это **не выполняет** запрос, а только строит план. Вывод выглядит как дерево операций, например:

```text
Seq Scan on users  (cost=0.00..431.00 rows=10 width=124)
  Filter: (email = 'test@example.com'::text)
```

---

## `EXPLAIN ANALYZE` — для реальных метрик

Чтобы увидеть **фактическое поведение** (время, реальное число строк), используют:

```sql
EXPLAIN (ANALYZE) SELECT * FROM users WHERE email = 'test@example.com';
```

**Важно:** `ANALYZE` реально выполняет запрос. Для `INSERT/UPDATE/DELETE` это опасно (данные изменятся). Безопасный шаблон:

```sql
BEGIN;
EXPLAIN (ANALYZE) UPDATE users SET status = 'active' WHERE id = 123;
ROLLBACK;
```

Типичный вывод:

```text
Index Scan using idx_users_email on users  (cost=0.29..8.30 rows=1 width=124) (actual time=0.015..0.017 rows=1 loops=1)
  Index Cond: (email = 'test@example.com'::text)
Planning Time: 0.083 ms
Execution Time: 0.028 ms
```

---

## Что означают ключевые поля в плане

- **`cost` (0.00..431.00)** — условная стоимость операции (не время, а «вес» для планировщика).  
  - `0.00` — стартовая стоимость (когда можно начать отдавать первые строки).  
  - `431.00` — общая стоимость (чтобы отдать все строки).
- **`rows`** — ожидаемое количество строк. Если сильно отличается от `actual rows` — статистика устарела или распределение данных нетипичное.
- **`width`** — средний размер строки в байтах.
- **`actual time`** (только с `ANALYZE`) — реальное время в мс.
- **`loops`** — сколько раз выполнялся этот узел (важно для JOIN).

---

## Расширенные опции (полезны для оптимизации и собеседований)

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE) SELECT ...
```

- **`BUFFERS`** — показывает, сколько страниц читалось из shared buffers и с диска. Помогает понять нагрузку на I/O.
- **`VERBOSE`** — выводит дополнительные детали (например, какие именно поля выбираются, откуда берутся).
- **`TIMING`** — можно отключить, если нужно снизить накладные расходы при замерах.

Пример строки с буферами:

```text
Buffers: shared hit=12 read=8
```
- `hit` — данные были в кэше PostgreSQL.
- `read` — пришлось читать с диска (медленнее).

---

## Частые типы операций и что они значат

- **`Seq Scan`** — полное сканирование таблицы. Нормально для маленьких таблиц, плохо для больших. Часто признак, что нужен индекс.
- **`Index Scan`** — чтение по индексу. Обычно быстро.
- **`Index Only Scan`** — данные есть прямо в индексе, таблицу не читают. Очень эффективно.
- **`Bitmap Heap Scan + Bitmap Index Scan`** — когда нужно много строк: сначала собирают «битовую карту» совпадений по индексу, потом читают строки из таблицы.
- **`Nested Loop / Hash Join / Merge Join`** — способы соединения таблиц. Выбор зависит от размера таблиц и наличия индексов.

---

## Практический пример: когда индекс реально помогает

Без индекса:

```sql
EXPLAIN SELECT * FROM users WHERE email = 'test@example.com';
-- Seq Scan, cost высокий, rows может быть большим
```

С индексом:

```sql
CREATE INDEX idx_users_email ON users(email);
EXPLAIN (ANALYZE) SELECT * FROM users WHERE email = 'test@example.com';
-- Index Scan, cost низкий, actual time маленький
```

Это тот самый кейс, который любят спрашивать на собеседованиях: «покажите, как индекс влияет на план».

---

## Связь с тем, что ты уже изучал

- **SQL (DISTINCT и др.)**: `EXPLAIN` покажет, делает ли база сортировку или использует хеш для `DISTINCT`, сколько памяти нужно.
- **PostgreSQL (создание таблиц, отношения, запросы)**: при проектировании индексов важно смотреть `EXPLAIN` на типичных запросах, а не гадать.
- **Подготовка к собеседованиям**: часто дают запрос и просят «рассказать, что делает план, где узкое место, какой индекс добавить».
- **Веб‑разработка (PHP/JS)**: если API начинает тормозить, `EXPLAIN` быстро покажет, где проблема: в JOIN, отсутствии индекса, полном сканировании большой таблицы.

## Как отвечать на собеседовании

- **«Что делает EXPLAIN?»**  
  «Показывает план выполнения запроса: какие операции, в каком порядке, ожидаемую стоимость, использование индексов. Это основной инструмент для диагностики производительности».
- **«Чем отличается EXPLAIN от EXPLAIN ANALYZE?»**  
  «EXPLAIN только строит план, не выполняя запрос. EXPLAIN ANALYZE реально выполняет запрос и показывает фактическое время, количество строк, использование буферов».
- **«Как понять, что запрос медленный по плану?»**  
  «Смотрим на высокую стоимость, Seq Scan на большой таблице, большое расхождение между estimated и actual rows, много reads в BUFFERS».
- **«Когда использовать BUFFERS?»**  
  «Когда важно понять, сколько данных читается с диска, а сколько из кэша — это влияет на реальную производительность».

## Пример для твоего уровня (с фокусом на типичные задачи веб‑разработчика)

Допустим, в админке ты делаешь поиск заказов по email клиента:

```sql
SELECT o.*, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE c.email = 'test@example.com';
```

План может показать, что соединение идёт без индекса по `email`, а таблица `customers` сканируется целиком. Решение:

```sql
CREATE INDEX idx_customers_email ON customers(email);
```

После этого `EXPLAIN (ANALYZE)` покажет `Index Scan` и заметное падение `Execution Time`.
